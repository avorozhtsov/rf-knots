# Обязательная часть стоимости и проверка бюджетов поиска

2026-09-21. Вывод из точной семантики `reference.apply` и `UnknotWitness.moves`,
не новая loss и не изменение текущего frozen MCTS. Нужен, чтобы следующая
оценка действительно проверяла L10/L1000, а не только очень тесные caps.

## Тождество для любого полного witness

Пусть исходные длина слова L, число нитей N; конечное состояние — пустая
однокосица. Обозначим числа ходов: c — CC, r — REDUCE, d — DESTABILIZE,
i — INSERT, s — обе STABILIZE, b — BRAID, k — COMMUTE, p — PASS.
Каждый semantic action считается одним ходом, включая CC.

Из изменений длины и числа нитей:

```
L = 2r + d - 2i - s
N - 1 = d - s
q0 = (L + N - 1) / 2
m = q0 + c + 2(i+s) + b + k + p
L_lambda = q0 + (lambda+1)c + 2(i+s) + b + k + p
```

Для knot closure q0 целое; replay проверяет это и завершение. Для префикса
аналогично `lambda*c_used + m_used + q(current)` равно q0 плюс уже накопленные
`(lambda+1)c_used + 2(i+s) + b+k+p`. Это точное переописание цены, не
штрафная эвристика против любых COMMUTE/BRAID: такие ходы могут быть
необходимы для решения. Потенциал не является полным remaining-cost oracle.

Если есть доказанная нижняя граница u_lower для u исходного узла, то

```
L_lambda >= q0 + (lambda+1)*u_lower.
```

Совпадение replayed reference cost с этой границей доказывает минимальность
его L_lambda **для данных semantic actions и данного исходного представления**.
Это не более общий топологический инвариант представления, не разрешение
использовать неучтённые бесплатные macro moves и не утверждение о policy.

## Предварительно найдено на текущей панели; нужен отдельный audit

Read-only подсчёт по уже построенным 64 roots дал `m_ref = q0+c_ref` во всех
64 случаях. У 40 из них signature/determinant lower совпадает с c_ref.
Таким образом, предварительно 40 reference costs уже достигают этой нижней
границы; до отдельного replay/counter audit не выдавать это за новый
проверенный certificate artifact. Остальные 24 не объявлять ни оптимальными,
ни неоптимальными: там неизвестно, можно ли снизить CC.

Joint нашёл только query 53 (L=70, N=3, c=1) при обеих λ; оба witness
отдельно воспроизведены, общий joint replay audit прошёл. Известный witness
имеет m=37, L10=47, L1000=1037; новые m=39/45 дают соответствующие излишки
стоимости 2/8. Проверить это по полным semantic action counters, а не только
по итоговым scalar costs. Parent не имел решения, поэтому common-success
cost delta отсутствует, а не равен этим числам.

## Что проверять до следующего cost-протокола

Текущий cap `max(64,m_ref)` даёт query 53 ещё 27 ходов, но у всех 26 roots
за пределами TRAIN size envelope cap точно равен m_ref. Величины в разных
размерных стратах поэтому смешаны с доступным запасом ходов.

Если c_ref=2, а настоящий u может быть 1, снижение CC иногда требует
больше zero-CC действий. Оно способно улучшить L1000 даже при существенно
более длинном пути, который прежний cap отвергает. Безопасность CC cap из
предыдущего envelope audit **не доказывает безопасность move cap**.

Следующий read-only audit должен:

1. Повторно воспроизвести все reference witnesses; проверить тождество
   по каждому semantic step/prefix и полным counters.
2. Сопоставить lower certificates с уже independently audited determinant/
   signature. Отдельно считать доказанно оптимальные reference costs и
   интервал-неопределённые случаи; не заменять upper на exact u.
3. Проверить реальные joint solutions и их excess относительно доказанной
   границы; source/checkpoint/panel/audit/shard hashes сохранить.
4. Для каждой λ вывести safe necessary move envelope для `L_lambda <= B`:
   `m <= B - lambda*u_lower`. Это универсальная верхняя граница числа ходов
   у любого пути с такой ценой, не существование самого пути. Сравнить с
   действующим cap; не увеличивать его посреди серии.
5. Использовать результат при новом заранее фиксированном протоколе поиска:
   отделить нахождение известного optimum, сокращение неизвестного CC и
   перенос на большие размеры. Отдельно учитывать число найденных решений,
   regret относительно известных optima, compute и цензурированные неуспехи.

Перед новым поисковым протоколом завершить текущие metric-control/uniform
и их audits; read-only проверку границы можно готовить параллельно. Ни эта
диагностика, ни формула не дают основания отбросить embedding или назначить
всем неуспешным траекториям отрицательные policy labels.
